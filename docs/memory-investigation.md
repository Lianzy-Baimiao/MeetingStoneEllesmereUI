# 内存增长调查（1.4.5 / 2026-10-02）

## 结论与边界

用户原观察：重载后约 8M，操作后最高三十多 M，无报错。
2026-10-01 收到 `游戏测试/测试.txt` 中同一轮操作的独立插件记录：

| 插件 | 手动 GC 前 | 手动 GC 后 |
| --- | ---: | ---: |
| MeetingStone | 30.69 MB | 7.03 MB |
| MeetingStoneEX | 26.15 MB | 1.20 MB |
| MeetingStoneEllesmereUI | 0.88 MB | 0.88 MB |

本次大部分增量能由 Lua 垃圾回收释放，更符合临时对象积累，不支持把该峰值直接
判定为无法回收的泄漏。美化插件在这次读数中保持 0.88 MB，但记账归属并不等于
因果归属，不能据此排除其他代码路径或长期保留增长。一轮数据不能证明“绝无泄漏”；
仍以多轮相同操作后的 GC 基线是否持续上升为判断依据。没有必要为这次峰值定时 GC。

已执行 `python MeetingStoneEllesmereUI/tests/profile_retention.py`，6 批×100 次
页面开关、搜索框借用/归还、活动类型切换、筛选开关、两设置页分类遍历与开关重绘，另加入首页两个开关及当前专精切换事件。
最终 493 个模拟 UI 对象（含纹理/字体）、209 个脚本 hooks、0 个待执行计时器，
各批均不增长。两次完整 GC 后约 1622.8–1623.2 KiB，没有持续保留增长。
这是 Lua 5.1 + WoW/EUI 合约替身的测量，不是游戏内插件占用，不能与 8M 作比较。
没有执行完整 EUI/Core/Widgets 自动遍历、真实搜索、动态成员列表或网络数据更新。

代码事实：
- 集合石 `Cache/Activity.lua` 的活动索引使用弱值表，不是单凭这个表就能断言泄漏。
- `Libs/NetEaseGUI-2.0/Embed/View.lua:GetButton(i)` 缓存按位置创建的行按钮；
  打开更长的列表会抬高已创建控件数量，后续复用。WoW Frame/Texture 不能像普通
  临时 Lua 表一样销毁，所以首次打开后的占用不一定回到刚重载的水平。
- 美化层 switch、settings、unified filters 与新首页图层均按对象缓存；重复操作探针
  未见控件/hooks持续增长。但模拟没有覆盖所有客户端路径，不作「绝无泄漏」承诺。

## 游戏内对照步骤

非战斗、非副本关键操作时进行；一次手动 GC 可能短暂卡顿。不要设置定时清理。

1. 重载后先打开将要测试的所有页面，让一次性 UI 缓存预热，再关闭弹窗。
2. 执行下列读取命令，记录三个插件各自占用：

```lua
/run UpdateAddOnMemoryUsage() for _,n in ipairs({"MeetingStone","MeetingStoneEX","MeetingStoneEllesmereUI"}) do print(n,format("%.2f MB",GetAddOnMemoryUsage(n)/1024)) end
```

3. 正常搜索、切换类型和筛选，记录到高值后再读一次；保持相同的最终活动类型。
4. 手动触发一次垃圾回收，再执行读取命令：

```lua
/run collectgarbage("collect");UpdateAddOnMemoryUsage()
```

5. 重复同一批操作至少三轮，比较每轮回收后的基线：明显回落且趋于稳定，更符合
   临时分配/有限缓存；回收后基线仍持续抬升，才更值得追踪保留对象（也可能是持续扩张缓存）。
6. 可再仅停用本美化插件、保留集合石/EX做同样对照，然后恢复。不要清空配置、不要
   禁用一批其他插件同时比较，以免混淆。插件内存归属及共享库记账不等于代码因果。

后续若怀疑长期增长，可补充三轮相同操作在 GC 后的数字，以及主要做了什么操作。
若聊天脚本被客户端策略阻止，改用你现有内存监控工具的读取/手动清理功能，不绕过安全限制。

本次没有修改真实 SavedVariables，没有注入自动内存采样、定时GC或清理集合石缓存。
